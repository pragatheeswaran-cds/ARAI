# Batch inference and job lifecycle

Version 1.8 (amended 2026-10-05) | Implementation baseline | Component INF

## Requirements and boundary

Bind dataset and active promoted or valid baseline hash at submission. Queue one worker. States queued->running->succeeded|failed; crashed running ->interrupted on restart. Queued can resume. Retry failed/interrupted creates new run with original bindings and new key.

Stages: validate snapshot ->features/graph/style ->eligibility ->frozen preprocessing ->score/reference percentile/rank/top5% ->evidence ->atomic publication. No results before succeeded. Results are written to PostgreSQL in the transaction that marks success, so a crash or a failed write leaves no partial output (component 14). Reconciliation interrupts only runs held by this worker identity and deletes no run directory. A run scored before version 1.7 whose result files are gone is reported as failed (output_missing). Each run records a drift report with its summary: the share of eligible customers at or above the training 50th, 90th, 95th and 99th score percentile, and the features whose median lies outside the training 10th-90th percentile range. It warns when the share above the 95th percentile leaves .025-.10, when an input is out of range, and when the scoring code differs from the code the bundle was published with. The report describes; it never refits, corrects or promotes. The worker loop survives a transient database error; in the single-process profile readiness is false when the worker has stopped.

Prediction fields include run_id/model_id/model_kind/dataset_id/world_id/cutoff/customer_id, eligibility_status, nullable raw_score/risk_score/rank, selected_for_review, nullable baseline_rank, baseline_selected, support_counts/evidence_refs/wardrobing. baseline_rank orders eligible customers by raw_return_rate under the standard tie rule and baseline_selected marks its top k, the same k as the model; ineligible customers get null/false; under baseline fallback they equal rank/selected_for_review. The run records model_only_count and baseline_only_count. Ineligible unranked scores null selected=false, but case evidence visible. Customer evidence includes source transactions, mature/raw/expected/value denominators, products, supported neighbors, separate wardrobing. Contract 1.6.0 (AM-57): the evidence stage groups the supported edges into communities (connected components; Louvain with a fixed seed only inside a component of thirteen or more members) and gives each the kind one stated rule over observed evidence yields (ring: a coordinated claim match on an edge, two or more members selected, or a member with a coordinated claim share above zero; household otherwise); the run records community_count and ring_count. The kind is evidence about the group, never a verdict on a member. Contract 1.7.0 (AM-58): after selection the evidence stage re-scores every eligible customer with the frozen pipeline once per feature family (claims, timing, expected_vs_actual, composition, volume; together the 43 model features) with that family at the bundle's training median, predict-side only, and records the score without it and whether the raw score stays at or above the raw score at rank k; it orders the evidence tags by those family deltas and evaluates the analyst rulebook's five rules from the bundle's training thresholds. Nothing is fitted and no score, rank or selection changes. Contract 1.9.0 (AM-60): per style the evidence stage also records the requests by reason code, the median return day, the share in the last five days of the window, the returners selected for review or in a ring and the median returner score, and per customer and style the lines bought and returned and the last reason code; sums over the same mature lines the style states read. Contract 1.11.0 (AM-62): after the run has succeeded and its results are published, the worker drafts one investigation memo per selected customer from the served case (no free text, no private truth, other customers' identifiers replaced by neutral labels) with the Anthropic SDK and structured output, behind a deterministic gate that checks every cited number against the case, the panels, the action and the names; two failed drafts give unavailable with the reason, and without an API key every memo is unavailable by design. Memos are a draft on top of the run and never change a score, rank or selection. Contract 1.12.0 (AM-63): the worker records when each stage began and, when a cancel was requested, stops at its next stage and marks the run interrupted (cancelled) with no result; a queued run is cancelled at once. No private truth or causal claims.

Fallback banner states actual failed gate or selection not completed; retain valid active model unless explicitly switched. Graph failure fails job, empty graph valid. Resource limits500,000,000 upload bytes,2,000,000 rows,one worker,page<=100,poll2seconds. Measure runtime/API latency on target machine before claims.

Contract 3.0.0 (AM-76): the tier gains CRITICAL, a customer selected for review who is a member of a detected ring; HIGH is every other selected customer. It is a presentation rule over stored results (the community kind of a selected customer), computed on read like the other tiers; no score, rank or selection changes.

Contract 3.1.0 (AM-77): scoring stores the snapshot's own aggregates in the run summary, made once from the tables it already reads. summary.insights holds orders, return requests and refunds by day, return lines by return channel, and purchased and requested units by category; summary.style_insights holds, per style, the pooled return rate of its category, the share of its requested units from its top 1, 5 and 10 percent of returners (cumulative, at least one account) and from the others, and purchased and requested units by order month. Flagged rows are those of customers selected for review: a description of the review set, never a finding about a return. No private truth is read and no feature, score, rank or selection changes; a run scored before 3.1.0 has no aggregates and serves empty lists.

Contract 3.2.0 (AM-78): scoring copies region, email and phone from customer_master beside each customer where the snapshot carries them (null otherwise). They are stored with the customer's other measures, shown on the screens and matched by the queue search; they are not in the bundle's feature order and never reach the model.

Contract 3.3.0 (AM-79): the evidence graph. Where the snapshot carries contact details, the links shown to an analyst are those of five identifier types: the address, device and payment method of the orders, and the phone number (its last ten digits) and the mailbox (the email address in lower case without a +tag) of the account. A value shared by more than 25 accounts is dropped, a placeholder or a missing value links nobody, and two accounts are linked when they share at least two types, so a shared phone alone links nobody. Every link of the three-identifier graph is a link of the evidence graph, and a snapshot without contact columns has exactly the three-identifier graph. The evidence graph gives the neighbours of a customer, the groups of linked accounts and their kind, the ring returners of a style, and the two evidence-only link measures (supported_neighbor_count, max_identifier_fanout) with the supported_links tag. Scores are computed before it is built; the model's inputs, the coordinated-claim evidence, the style verdicts, the ranks and the selection are those of the three-identifier graph, and a test scores one snapshot with and without its contact columns and requires them equal. Because a ring makes a selected customer Critical and Escalate, the wider graph can raise those two presentation labels; it cannot change who is selected. The kind rule reads the shape of an edge: an edge that shares a payment method, or shares no address, is not the shape of a household, and such a group is a ring on one matching claim, two selected members or a positive coordinated-claim share; a group whose every edge shares an address and no payment method needs two matching claims or two selected members (AM-66 unchanged for every snapshot without contact details, where an edge without an address always has a payment method). The run summary records contact_link_edges, the links the model's graph does not have.

## Inputs, outputs and dependencies

- Inputs: Registered complete dataset, optional eligible model, idempotency key.
- Outputs: Run-bound predictions and evidence.
- Dependencies: Validation/features/artifacts/PostgreSQL.

## Acceptance criteria

| ID | Pass condition and required evidence |
|---|---|
| INF-AC-01 | Submission acknowledgement precedes scoring completion and stages persist. |
| INF-AC-02 | Duplicate scoped key/body returns same resource; changed body409. |
| INF-AC-03 | Crash cannot publish partial success; restart preserves notes/bindings. |
| INF-AC-04 | Population counts and eligible/ineligible nullable fields reconcile. |
| INF-AC-05 | No-winner path yields complete labelled baseline evidence; corrupt active model fails. |
| INF-AC-06 | baseline_rank/baseline_selected use the same k and ties as the model, equal rank/selection under fallback, and the run counts match the comparison filters. |
| INF-AC-07 | A run records its drift report; shifted scores or inputs and a changed scoring code each raise a warning, and a snapshot like training raises none. |

Acceptance status is recorded per criterion in acceptance-register.csv (status, evidence, date, reviewer). Prose requirements are not implementation evidence.

Contract 1.14.0 (AM-66): the community kind is `scoring.community_kind`. Where some edge shares a payment instrument a community is a ring on one coordinated claim match, two or more members selected for review, or a member with a coordinated claim share above zero; where every edge shares only an address and a device it is a ring only with two or more coordinated claim matches or two or more members selected for review. Observed evidence only; scores, ranks and selections are unchanged.

Contract 1.15.0 (AM-68): each snapshot of a world is scored on its own, with the bundle bound at submission; nothing is carried from one snapshot's scores to the next. `arai snapshot <world> --as-of <date>` writes an earlier snapshot of a generated world by replaying the generator's stages for its seed and settling the same planned timelines at the earlier date with the generator's own rules (src/arai/snapshots.py); the generator package is unchanged, the earlier snapshot passes the same validation as any upload, and the command checks that it is a prefix of the world on disk.
