# React/Vite frontend and analyst workflows

Version 1.8 (amended 2026-10-05) | Implementation baseline | Component UI

## Requirements and boundary

Use React/Vite for implementation. Standalone wireframe is interactive specification, not production code. Rewrite components with typed API; never ship inline mock metrics. Prototype runs offline without external fonts/assets and labels illustrative data.

The Upload and Score screen shows the seven-file checklist built from the data schema's table names (422 upload.missing_part rows mapped onto it), grouped validation reasons from the 422 details (validation stays blocking), the stepper as ingest, features, detection, investigation mapped from the real stages with elapsed times from stage_log, a cancel for a queued or running run, and the done summary with eligible and selected counts, community_count, ring_count and styles_with_verdict. Implemented against contract 1.12.0: a run strip (dataset, scored and alert counts against the budget, queue threshold, memo progress, reviewer name kept in the browser), the case queue with tier, recommendation, primary-signal chips, linked-account group, workflow status, the approval band excluding the reviewer's own cases, a cleared-heavy-returners view with the templated reason and ring grouping; the case with its score breakdown and counterfactual, expected-vs-actual band, return behaviour table, linked-account group with members and edges, memo by status, decision panel whose refusals are shown as the server words them, and threshold slider over the score distribution with the synthetic second line when the run is on the demonstration world; SKU intelligence with the five verdicts, reasons, the four drawers and the headline pair; the evaluation hero curves and run manifest; upload with the file checklist, the four-step stepper from stage_log, cancel and the done summary. Every rule the UI derives lives in web/src/derive.ts. Routes: /overview, /datasets, /runs/:run_id/customers, /runs/:run_id/customers/:customer_id, /runs/:run_id/styles, /runs/:run_id/styles/:style_id, /experiments/:experiment_id. Default dataset selection when no ready run. Persistent run/model/cutoff/synthetic context. Support back/deep links. Snapshot cutoff immutable; evidence date filters never recompute historical risk.

Contract 1.13.0 (AM-64): the Cleared heavy returners view asks the server (cleared_heavy) and shows full pages; filter changes push history entries so Back returns to the previous view; the decision panel refuses approve or reject without a reading before any request; the case tabs follow the tabs pattern (arrow keys, one tab stop); every screen sets document.title; a run cancelled on purpose reads cancelled with no retry prompt; a dataset nothing was scored on has a Remove action; long unbroken note text wraps.

Contract 1.14.0 (AM-66, AM-67): the Overview shows refunds paid to the model's queue and to the rule's set, with the part on transaction claims, labelled as observed refunds and not losses; the queue shows each customer's refunds under the requested units, and an Export this view as CSV link for the current filters; cleared rows and the case's cleared callout say what was not observed (no repeated transaction claims, no late returns, no linked accounts); the case shows a Refunds paid row and a Download case summary button (plain text built in the browser from the page).

Contract 1.15.0 (AM-68): the workspace opens on the newest succeeded run of the latest snapshot. The queue's Status column becomes Status / history (earlier decision, and 'also in the 09 Aug 2026 queue', 'new to the queue since', 'left the queue since' or 'new account since'), with a History filter when the run has a previous snapshot. The case has a History tab (the customer in each snapshot: rank, score, recommendation, units, refunds, linked accounts, how the review ended, notes, with a link to the case in that snapshot) and a callout when an earlier snapshot's review ended in a decision; notes say which snapshot they were written on. The Overview shows the review set against the previous snapshot; Datasets and runs name each snapshot by its cutoff date.

Contract 1.16.0 (AM-69): the app opens on a sign-in page (the development login's people with their roles, or a Keycloak button on single sign-on) and shows the signed-in person, roles and Sign out instead of a reviewer name box; a 401 returns to sign-in. Actions follow the role: no registering or scoring without admin, no export or case summary without reviewer, no notes or decisions for a viewer or admin, no Approve or Reject without approver, and the approval band hides the cases the signed-in user opened. Notes say (signed in) or carry an unverified name marker for reviews written before sign-in existed. The CSRF token is kept in memory and sent on every POST and DELETE.

Contract 1.17.0 (AM-70): under single sign-on the sign-in page shows one Sign in with Keycloak button that returns to the page the person was on, and explains a refused sign-in in words (no ARAI group, attempt expired or reused, Keycloak did not complete it, answer not verifiable, Keycloak unreachable) before taking the code off the address. Sign out also ends the Keycloak session through Me.sso_logout_url.

Contract 2.0.0 (AM-71): an admin sees People & access in the navigation: everyone who has signed in with each role and where it comes from (Keycloak group, bootstrap admin, development list), status, last sign-in, last activity and open sessions, with Disable, Enable and End sessions behind a confirmation that says what the action does and takes an optional reason; the admin's own row offers no Disable. A note says roles are not edited in ARAI and where they are. Below it, the sign-in log, filtered by kind and person, with each entry described in words and older entries on request. The sign-in page explains user_disabled. The queue no longer sends exclude_reviewer.

Overview has eligible/excluded/selected counts, model kind and evaluation status. It lists customers selected by the model but not by the return-rate rule, and the reverse, with counts; queue and case show the return-rate rank beside the model rank. Wording on these surfaces stays neutral (selected by / not selected by); caught, missed and cleared appear only on the evaluation page. Under baseline fallback the comparison is hidden. No loss prevented or operational FPR without labels. The evaluation page draws the hero curves from GET /experiments/{id}/curves (abusers caught and legitimate heavy returners reviewed over k, both rankings, marker at review_budget) and shows the run manifest from ExperimentSummary (git_sha, seeds, config_hash) beside the dataset hash; ablation rows are the real slice (claims, timing, both) and the ceiling appears only if a ceiling.* metric exists. Queue defaults selected-for-review; search opaque ID, eligibility/all filters, measured evidence tags and review disposition. Score tooltip distinguishes training percentile, batch rank and probability. Tiers are the served HIGH/MEDIUM/LOW anchored to the queue, never fixed percentile bands; the gate outcome is shown as a stated presentation rule, not a model output; the score breakdown is worded as the score with a family at typical values, never as parts that sum to the score; the primary signal chips are the served primary_signals; there is no first or second pass panel (one pass exists; the return-rate rank sits beside the model rank).

Case shows observed-vs-expected quantities/denominators with the normal band (expected +/- 2 sd) and, for a customer outside the queue, the one-line cleared reason rendered from its template key, timeline, style links, supported relationship table with same-style claim timing, the customer's community (its members with their own scores and the edges between them, drawn as one group with its ring or household kind and the group's return rate on mature lines derived from the member sums; the queue can group and filter rows by community), independent wardrobing with integer score and fired signals, and append-only notes. The investigation memo is shown only with status ok, labelled as a draft with its model and time in the audit footer; pending, unavailable (with the reason) and not_selected each have their own state and the screens look right with every memo unavailable. Say suspected/indicator, not detected fraud type/confidence. Review corrections append; notes cross runs of same world/customer and retain origin model/run. The case shows the served workflow state and who opened it; a reviewer who opened a case sees that another person must decide it, and the server's 409 message is shown as it is; the approval band lists awaiting_approval cases excluding the reviewer's own; LOW and cleared cases take agree/disagree feedback that never moves the state. No trained labels.

Style queue primary; quality/targeting/mixed/no-elevated-signal/insufficient/no-return states, continuous axes (damage share, claim share, linked-claim share, linked claimants), support, customer links, SKU drill-down; the style's name, top reason codes with their group, timing (median return day, share late in the window), the flagged-returner share and ring returners as shares of returners, and the returners drawer with each returner's own score, tier and community. Product evidence never clears customer automatically. All products apparel/INR.

Evaluation opens with the caveats before any result: simulated data, the two signals the model leans on with the precision without each and without both, the honest group the model reviews more often than the rule, the range across the stress worlds, and whether the development target was met. The page selects metrics by code, ranking and slice, never by their wording, and says so when the dependence or stress step was not run. Case pages state in plain words what the record shows and does not show (return rate against expected, claims, late returns, linked accounts with matching claims) without a conclusion. Evaluation: baseline/all candidates, coverage/gates/rejection reasons, selection separate from final-test status, benign FPR/denominators, action recall,1/5/10% sensitivity, uncertainty, report-only style/wardrobing, report-only references (analyst rulebook, volume-only), the error account and the difficulty-calibration disclosure. Truth reveal only here and labelled simulation.

Dataset page shows manifest validation/cutoff/history/schema; run progress/errors/retry/hash; no training button. Persistent baseline banner and label; missing bundle blocks run. Loading/empty/error/insufficient-evidence states on every data surface. Labelled keyboard controls/focus/table headers, non-color status labels, responsive layout required.

Local identity notice: no authenticated reviewer. VM shared login still free-text attribution. Replace PDF employee profile with reviewer-name input. Remove fake notifications and unsupported bulk enforcement. Preserve useful PDF sidebar/table/case structure with documented changes.

## Acceptance criteria

| ID | Pass condition and required evidence |
|---|---|
| UI-AC-01 | Walkthrough traverses dataset/run/queue/case/style/SKU/notes/evaluation with stable context and back. |
| UI-AC-02 | Prototype opens offline via file://; production consumes API instead of inline metrics. |
| UI-AC-03 | Fallback/loading/failed/empty/insufficient-history states truthful and distinct. |
| UI-AC-04 | No AI confidence/USD/non-apparel/calibrated bands/loss-prevented claims remain. |
| UI-AC-05 | Keyboard user filters, opens cases, navigates tabs, appends note and returns. |
| UI-AC-06 | Implemented notes persist cross-run; prototype labels memory-only behavior. |
| UI-AC-07 | Truth reveal isolated to evaluation; examples never presented as measured results. |
| UI-AC-08 | Rank comparison appears on overview/queue/case with neutral wording and is hidden under fallback; evaluation shows references, error account and calibration disclosure. |
| UI-AC-09 | Evaluation finds every figure by code, ranking and slice with reworded names; it leads with the claim and timing dependence, the repeat-claimant review rates and the stress range; the datasets page shows the worker state and the queue. |

Acceptance status is recorded per criterion in acceptance-register.csv (status, evidence, date, reviewer). Prose requirements are not implementation evidence.
