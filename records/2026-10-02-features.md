# Feature engineering record, 2026-10-02

Implementation of specification component 06 (v1.4) and the exploration of the engineered features.
Source: `src/arai/features.py`, `src/arai/dataset.py`, `src/arai/feature_eda.py`,
`notebooks/03_feature_engineering_and_eda.ipynb`, tables under `reports/features/2026-10-02/`. Simulated data
only. Numbers are from the worlds regenerated under amendment 1.4.

## What exists

- **17 model features** in the order of `contracts/features.yaml`, one row per customer and world, computed from
  the seven operational tables only. Identifiers are used for equality alone.
- **2 evidence-only link measures** (`max_identifier_fanout`, `supported_neighbor_count`): computed and shown to
  the analyst, never given to a model (AM-26).
- **Relationship graph**: an edge needs two shared identifier types; a value shared by more than 25 accounts is
  dropped; an empty graph is valid.
- **Style and SKU evidence**: quality and targeting signals with the six states.
- **Wardrobing indicator**: built on late item returns, integer points, independent of the model score (AM-28).
- **Frozen training reference**: category return rates, the fallback for a category without peers in a
  snapshot. Everything else is an aggregate of the snapshot being scored.
- The feature path reads operational tables only (`dataset.load_operational`); a test builds the features with
  private truth changed and then removed and gets the same file. Labels are joined afterwards.
- 23 tests on hand-calculated fixtures.

A world of 10,000 customers takes about 4 seconds. In all 20 development worlds no category lacked peers, so
no model feature depends on the frozen reference and cross-validation folds can share the feature files.

## Two changes to the feature set, and why

Both were decided on training worlds, before any validation world exists, by fitting the logistic and the
smaller boosted candidate out of fold by world (precision at the 5% budget, gate legs against the return-rate
rule; `probe_variants.py` in the session scratchpad, numbers repeated in `records/2026-10-02-gate-dry-run.md`).

| Feature set | Logistic | Boosted (15 leaves) | Gate |
|---|---|---|---|
| 18 features of v1.3 (with the two raw link measures), v1.3 worlds | fails household leg | fails household leg (0.063 against 0.042) | fail |
| 16 features (AM-26: link measures evidence-only) | 0.552 | 0.652 | pass |
| **17 features (AM-27: plus `late_return_lines`)** | **0.614** | **0.694** | **pass** |
| 17, `residual_z` replaced by `excess_rate` (raw minus expected) | 0.611 | 0.689 | pass |
| 17 plus `excess_rate` | 0.614 | 0.694 | pass |
| 17 plus accounts sharing a payment identifier | 0.656, fails household leg | 0.724, household 0.034 against 0.039 | not robust |
| 17 plus claim lines per order, or claim-line count | 0.637-0.672 | 0.700-0.702 | pass |

- **AM-26, link measures out of the model.** Households are the main honest source of supported links, so a
  model given raw link counts selects honest household members more often than the return-rate rule does. The
  model now sees links only through `coordinated_claim_share`, which needs linked accounts to act.
- **AM-27, `late_return_lines` in.** A count of item returns requested in the last quarter of the return window
  (and still inside it). Customer-level medians and shares hide behaviour that shows on single lines: recall of
  temporary-use abusers at the 5% budget rises from 0.52 to 0.64 for the boosted model.
- **Not adopted.** Replacing or supplementing `residual_z` changes nothing measurable. A payment-sharing feature
  adds three points but brings the household leg to within 0.006 of failing for the boosted model and fails it
  for the logistic one, so link structure stays evidence-only. Claim-frequency features add less than a point
  to the boosted model; the feature set was not grown for that.

## What the features show (ten training worlds, 56,615 eligible customers, 3,181 abusers)

| Feature alone | AUC | Range across worlds |
|---|---|---|
| requested_refund_ratio | 0.80 | 0.79-0.82 |
| raw_return_rate | 0.79 | 0.78-0.81 |
| residual_z | 0.79 | 0.78-0.80 |
| claim_share (where defined) | 0.78 | 0.77-0.81 |
| late_return_lines | 0.63 | 0.61-0.65 |
| late_window_share (where defined) | 0.62 | 0.61-0.65 |
| mature_sale_lines / log_order_count | 0.56 | 0.54-0.58 |
| evidence only: max_identifier_fanout / supported_neighbor_count | 0.71 / 0.66 | |

1. **`residual_z` is not a volume-free, product-adjusted rate.** The expected rate barely varies between
   customers (mean 0.20 in every group), so the residual is close to the raw rate (both AUC 0.79) scaled by the
   square root of the number of units. It does separate defective-product buyers from heavy returners on
   average (mean 0.10 against 2.87), but alone at the 5% budget it selects defective-product buyers more often
   than the raw rate does, because they buy more. Inside the models this does not show: the boosted model's
   false-positive rate for defective-product buyers is 0.026 against 0.060 for the rule. The screen must not
   describe the residual as "adjusted for defective styles".
2. **No single feature sees every kind of abuse** (`auc_by_abuse_type.csv`). `claim_share` separates ring and
   solo claimants (0.95, 0.94) and is blind to temporary use (0.52). `late_return_lines`,
   `late_window_share` and `median_window_ratio` see temporary use (0.83-0.84) and are blind to claimants.
   `coordinated_claim_share` sees only rings (0.75). This is the plain reason a one-number rule cannot do the
   job.
3. **Missing evidence is itself evidence.** 20% of honest eligible customers have no return request at all,
   against none of the abusers; `coordinated_claim_share` is undefined for 81% of honest customers and 25% of
   abusers. The missing-value indicators carry real weight, and the explanation shown to an analyst should say
   "has claims" as well as "high claim share".
4. **Volume is a weak shortcut** (0.56), and recency features carry almost nothing (open_window_share 0.52,
   trend_90d 0.49).
5. **Stability.** Feature means differ by a few percent between worlds. For features whose mean is near zero
   the relative range is large (`trend_90d`, `residual_z`), which says nothing about their stability.
6. **Three of the four strongest features are near-duplicates** (rank correlation 0.87-0.95 between raw rate,
   residual and refund ratio). A tree model will split among them almost arbitrarily, so feature-importance
   displays must group them.

## Honest look-alikes and hard-to-see abusers (`lookalikes.csv`)

| Group, eligible customers in ten worlds | Customers |
|---|---|
| Honest | 53,434 |
| Honest ring members with no completed action yet | 298 |
| Honest with any claim line | 10,356 |
| Honest repeat claimants (two or more claim lines) | 3,897 |
| Abusers | 3,181 |
| Abusers with two or more claim lines | 1,790 |
| Abusers with exactly one completed action | 921 (29%) |
| Abusers with no claim line (temporary use only) | 800 |

There are more than twice as many honest repeat claimants as abusers with repeat claims. They are mostly
customers at addresses where deliveries genuinely fail. This is the dominant honest look-alike, ahead of heavy
returners, and it is what limits precision. The 298 ring members who have not acted are honest by label and
linked like a ring; the trained model selects 2 of them, so they are not a visible source of error.

## The wardrobing indicator (AM-28)

The first version scored customer-level averages (mean timing score, median window ratio) and found one
temporary-use customer in eight. The independent review traced this to the aggregation and proposed counting
late lines. Measured on training worlds before adoption, then in the notebook:

| Band | Flagged | Really temporary use | Precision | Recall |
|---|---|---|---|---|
| elevated (two or more late returns) | 419 | 394 | 0.94 | 0.32 |
| elevated or possible | 988 | 693 | 0.70 | 0.57 |
| previous rule, elevated (v1.3 worlds) | 598 | 143 | 0.24 | 0.13 |

False alerts: 289 of 53,434 honest eligible customers (0.5%); 30% of the 955 honest customers who have any late
item return. A request after the window is not a late return, which is what keeps honest late requests out.

**A limit that must be said out loud.** The rule is this precise because in the simulation honest item returns
follow one timing law (most in the first half of the window) and temporary-use returns another (most in the last
third); about one honest item return in two hundred falls in the last quarter of the window. Real customers
procrastinate. On real data this rule would be far noisier, and the same is true of the model's
`late_return_lines` feature. The indicator stays report-only.
